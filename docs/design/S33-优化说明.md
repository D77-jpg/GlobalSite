# S33 优化说明（草案，待确认后实施）

> 目标：在不破坏现有安全、多租户、计费与事实门禁的前提下，提升 **AI 生成成功率与质量、生成速度、代码可维护性、上手体验**。
> 约束沿用 AGENTS.md：不升级无关依赖；API 变化先改 foundation.openapi.yaml；完成 typecheck / build / lint / test，前端改动跑 e2e。
> 分支建议：`feat/s33-agent-quality`。

---

## 一、现状诊断（依据代码与 S23 验收）

| 问题 | 证据 | 影响 |
| --- | --- | --- |
| 模型输出格式不稳定 | `site-agent-provider.service.ts` 仅靠提示"Return ONLY JSON"，未使用 `response_format`，未设 temperature；S23 记录"真实模型多次返回格式/内容不合格结果" | 重试多、浪费 Token、等待长 |
| 整页一次性生成 | design/content/refine 任务 `max_tokens = 32768`，失败整页重来 | 慢、贵、失败面大 |
| 单一模型 | 组织仅一个 `AgentAiProvider`，当前 deepseek flash 无视觉 | 视觉审查闭环实际未生效 |
| 核心文件过大 | `site-agents.service.ts` 2348 行 / 93KB；`web/src/sites.tsx` 3764 行；`design-system.css` 4231 行 | 改动风险高、提示词难迭代 |
| 类型松散 | TS/TSX 中约 693 处 `any`，`processSiteAgent(task: any)`、`run: any` | 重构易出隐性 bug |
| 样式与包体 | 5+ 套 CSS 并存（S20/S29/S30 多轮重构残留）；Vite 主包 >500KB | 加载慢、样式冲突 |
| 流程重 | 定位→事实→访谈→地图→提案→审核→质量审查→构建→发布 | 外贸用户难以走完 |
| 首页过长 | VELATURO 首页 6000–7000px | 转化与移动端体验差 |
| 仓库杂物 | `.cache/` 15MB gitleaks.exe + 扫描报告；`storage/verification` v7–v10 多版脚本 | 噪音 |

## 二、优化项与实施方案

### P0-1 结构化输出与容错解析（收益最大，改动小）

文件：`server/src/services/site-agent-provider.service.ts`、`agent-json.service.ts`、`ai-target.ts`、AI 设置模型/页面

1. AgentAiProvider 新增可选字段 `outputMode: "json_schema" | "json_object" | "prompt"`（默认 `prompt`，旧数据兼容，无需迁移）。
2. 请求体按模式附加：
   - `json_schema`：由现有 zod schema 通过 `z.toJSONSchema()`（zod v4 自带）生成 `response_format: { type: "json_schema", strict: true }`；
   - `json_object`：`response_format: { type: "json_object" }`；
3. 按任务设置 `temperature`：research/interview/review 0.2，design/content 0.7，rewrite 0.5。
4. `parseAgentJson` 失败时先用已有依赖 `jsonrepair` 本地修复一次再 zod 校验，修复成功不再计费重试；记录 `invalidReason: "repaired"` 诊断。
5. 测试：三种模式请求体快照、截断/围栏/尾逗号修复、修复后仍不合格走原重试路径。

预期：格式失败率显著下降（目标 <5%），重试 Token 减少。

### P0-2 分层生成：大纲 → 区块并行

文件：`site-agents.service.ts`（design/content 步骤）、`page-validation.service.ts`

1. 每页拆两阶段：`outline`（区块 key/类型/目的/事实引用，≤4k token）→ 每区块 `block` 生成（≤4k token）。
2. 区块单元复用现有 step/attempt/operationId/fencing 与"已计费成果保留"机制；同页区块以受限并发（默认 3，可配）执行。
3. 校验失败只重做该区块；页面级组装后再跑原 `validateGeneratedComposition`。
4. 首页区块预算：默认 ≤8 区块、校验规则中加入"首页估计高度"警告（基于区块类型权重），超出时在大纲阶段要求合并。
5. 兼容：旧 run 继续按整页逻辑执行（按 run 版本号分支）。

预期：单页生成时间下降约 40–60%，失败重做成本降为单区块。

### P0-3 按任务路由模型

1. AI 设置支持"任务模型映射"：`research/interview → 经济模型`、`design/content → 主模型`、`review → 视觉模型`（已有 `visionModelName` 字段扩展为路由表，可空即回退主模型）。
2. 审查任务在配置视觉模型时真正发送截图（现有 images 分支），报告标注 `reviewMode: visual`。
3. 用量统计按模型分开展示。

### P1-1 拆分 site-agents.service.ts

目标结构（行为不变、先补类型后搬迁）：

```
server/src/services/agents/
  types.ts            AgentRun / AgentStep / InputSnapshot 强类型
  runtime.ts          fenceRun / ownRun / processSiteAgent 调度骨架
  billing.ts          用量预留/结算/未知暂停
  steps/research.ts
  steps/interview.ts
  steps/design.ts     含 outline/block
  steps/review.ts
  steps/rewrite.ts
  prompts/*.md        提示词模板（随 Worker 发布，可版本化）
  validation.ts
site-agents.service.ts  仅保留对外导出（路由无需改动）
```

验收：现有 `sites.test.ts`、`business-design.test.ts`、`worker-lanes.test.ts` 全部不改即通过。

### P1-2 类型收紧

- 优先消除 agent/publishing/inquiry 核心链路的 `any`；ESLint 对 `server/src/services/agents/**` 开启 `@typescript-eslint/no-explicit-any: error`，其余目录 `warn`。
- 目标：`any` 数量从约 693 降到 <250。

### P1-3 前端瘦身

1. `sites.tsx` 按 Tab 拆分（定位/内容/设计/审查/发布/询盘），路由级 `React.lazy` 拆包，目标主包 <300KB gzip 前。
2. 统一设计令牌到 `web/src/ui/design-system.css`，删除未被引用的选择器（用 Playwright 覆盖率 + 选择器扫描确认），合并 obsidian-studio / workspace-layouts / product-ui 重复规则。

### P2-1 "一键出站"快速通道

- 入口：新建站点时可选"快速生成"——输入旧站网址或上传产品表 + 选择行业。
- 后台串联：旧站读取 → 自动事实候选（标记待确认）→ 地图 → 大纲/区块生成 → 结构审查 → 登录预览。
- 门禁不放松：未确认事实不进入商业声明，仅允许预览；正式发布仍需人工审批。
- 目标：首次可预览 ≤10 分钟。

### P2-2 真实回归基准

- 建 3–5 个不同行业的脱敏真实样例（机械、纺织、消费品、建材），固定输入快照，记录：格式失败率、Token、耗时、首页高度、人工评分。
- 每次提示词/模型改动跑基准并对比，结果写入 `docs/verification/`。

### P3 仓库清理

- 删除 `.cache/gitleaks/*.exe/zip`（CI 自行下载）；核实 `.cache/staged-secrets.json` 第 20 行标记是否真实密钥，若是立即轮换。
- `storage/verification/` 仅保留最新 `actual-quality-v10.mjs`。
- README 精简为产品简介 + 快速开始，分阶段记录移入 `docs/CHANGELOG.md`。

## 三、实施顺序与里程碑

| 阶段 | 内容 | 预估 | 风险 |
| --- | --- | --- | --- |
| M1 | P0-1 结构化输出 + P3 清理 | 1–2 天 | 低：可配置、默认兼容 |
| M2 | P1-2 Agent 类型 + P1-1 拆分（行为不变） | 3–4 天 | 中：靠现有测试兜底 |
| M3 | P0-2 分层并行生成 + P0-3 模型路由 | 4–6 天 | 中：计费/续跑需补测试 |
| M4 | P1-3 前端瘦身 | 3 天 | 中：e2e 兜底 |
| M5 | P2-1 一键出站 + P2-2 基准 | 5–7 天 | 中：产品流程变化 |

每个里程碑独立 PR，均执行 typecheck / build / lint / test，涉及前端的跑 Compose + test:e2e + test:quality。

## 四、不做的事

- 不改 CRM 契约与连接逻辑；不升级 React Router 7 / Express 5。
- 不放松事实门禁、审批与鉴权；不改动已有计费记录与历史任务。
- 不删除 storage 中的真实素材与截图。
